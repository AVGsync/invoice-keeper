# Invoice Keeper — план решения

Документ описывает, как решение работает целиком: доменные правила, база, бэкенд, веб-панель,
Telegram-бот и Mini App, запросы на естественном языке, дополнительные фичи, демо и порядок работ.
Источник требований — PDF кейса в корне репозитория.

Обозначения приоритета:

- **P0** — обязательно по кейсу, без этого решение не принимают;
- **P1** — дополнительные баллы из списка жюри;
- **P2** — наши «вау»-фичи (запросы на естественном языке, Mini App и пр.).

## 0. Состояние на сейчас

Что уже есть в `backend/`:

- Go 1.26, chi, PostgreSQL 16, golang-migrate, JWT (access + refresh в HttpOnly-куках, ротация refresh),
  bcrypt, rate limit, CORS, graceful shutdown, Docker + GHCR + nginx с TLS.
- Админ из `.env` (`ADMIN_LOGIN` / `ADMIN_PASSWORD`) создаётся или синхронизируется при старте.
- Маршруты приведены к кейсу:

| Метод | Путь | Кто | Статус |
|---|---|---|---|
| POST | `/api/v1/auth/login` | все | готово |
| GET | `/api/v1/auth/me` | авторизованные | готово |
| POST | `/api/v1/auth/logout` | все | готово |
| POST | `/api/v1/auth/refresh` | все (по refresh-куке) | готово, доп. эндпоинт |
| GET | `/api/v1/users` | admin | готово |
| POST | `/api/v1/users` | admin | готово: создаёт **только** `role=user` |
| PATCH | `/api/v1/users/{id}` | admin | готово: админа менять нельзя → 403 |
| DELETE | `/api/v1/users/{id}` | admin | готово: админа удалять нельзя → 403 |

Устранённые расхождения (проверено на живой БД):

- `POST /users` больше не принимает `role`: поле игнорируется, создаётся обычный пользователь.
- Учётку администратора через API не изменить и не удалить (`403 admin account is managed via .env`).
- `PATCH /users/{id}`: несуществующий id → 404 (было 500), занятый логин → 409 (было 500).
- `id` не UUID → 400 (было 500 от Postgres).
- TTL refresh-токена и `Max-Age` кук берутся из `TTL_ACCESS_TOKEN` / `TTL_REFRESH_TOKEN` (было зашито 1 ч / 7 дней).
- `/auth/me` отдавал `created_at = 0001-01-01` — исправлено.

Чего нет (это и есть основная работа): регулярные платежи, периоды, итоги, напоминания, Telegram,
Swagger, тестовые данные, веб-панель.

## 1. Как всё работает — общая картина

```
                 ┌──────────────── nginx (TLS) ────────────────┐
 браузер ───────▶│  /            → Nuxt (веб-панель, SPA)       │
 Telegram WebView│  /tg/*        → Nuxt (Mini App, тот же билд) │
                 │  /api/*       → backend :8080                │
                 └──────────────────────────────────────────────┘
                                         │
              ┌──────────────────────────┼───────────────────────────┐
              │ backend (Go, один бинарник)                          │
              │  HTTP API ── services ── repositories ── PostgreSQL  │
              │  scheduler (горутина):                                │
              │    • генерация периодов                               │
              │    • напоминания (outbox → Telegram / email / webhook)│
              │  telegram bot (long polling): кнопка «Оплачено»,      │
              │    команды, привязка аккаунта                         │
              │  assistant: Claude API + tools поверх тех же сервисов │
              └──────────────────────────────────────────────────────┘
```

Основной поток:

1. Админ создаёт **регулярный платёж** (шаблон): название, сумма, валюта, дата ближайшей оплаты, периодичность.
2. Бэкенд сразу **материализует периоды** (`payment_occurrences`): у каждого периода своя дата срока и своя отметка оплаты.
3. Планировщик раз в минуту:
   - дозаполняет будущие периоды (новый период не трогает прошлые);
   - ищет неоплаченные периоды, до срока которых ≤ 3 дней, и по которым ещё не было напоминания → пишет в Telegram-чат.
4. Пользователь видит общий список, отмечает «Оплачено» с фактической датой (в вебе, в Mini App или кнопкой прямо в сообщении бота).
5. Просрочка **не хранится**, а вычисляется из `due_date`, `paid_at` и «сегодня» в часовом поясе приложения — поэтому исправление даты оплаты сразу пересчитывает просрочку.

## 2. Доменные правила (P0)

### 2.1. Понятия

| Понятие | Где живёт | Суть |
|---|---|---|
| Регулярный платёж | `recurring_payments` | Шаблон: что, сколько, в какой валюте, с какого числа, как часто. Можно прекратить (soft delete). |
| Период (платёж) | `payment_occurrences` | Конкретный срок оплаты: `due_date`, снимок суммы и валюты, `paid_at`. |
| Оплачено | `paid_at IS NOT NULL` | Подтверждено, указана фактическая дата. |
| Не оплачено | `paid_at IS NULL` | При отмене отметки дата очищается. |
| Просрочка | вычисляется | Со следующего дня после срока; оплата в день срока — вовремя. |

### 2.2. Даты и часовой пояс

- Один часовой пояс на всё приложение: `APP_TIMEZONE` (по умолчанию `Europe/Moscow`). tzdata уже вшита в бинарник.
- «Сегодня» = `time.Now().In(loc)`, обрезанное до даты. Всё сравнение — по датам (`DATE` в БД), без времени.
- В коде — интерфейс `Clock` (реальный и фейковый для тестов и демо, см. `DEMO_TODAY`).

### 2.3. Периодичность и «нет такого числа»

- Обязательная — ежемесячно. Дополнительно (на наше усмотрение): раз в квартал, полгода, год.
  Храним `interval_months ∈ {1, 3, 6, 12}`.
- Храним **якорный день** `anchor_day` = день из первой даты. Срок n-го периода:

```
месяц_n   = месяц(first_due_date) + n * interval_months
due(n)    = min(anchor_day, последний_день(месяц_n))
```

- Пример: первая дата 31.01.2027 → 28.02.2027 → **31.03.2027** → 30.04.2027.
  Якорь не «съезжает» на 28-е после февраля — это частая ошибка, обязательно покрыть тестом.
- Високосный год: 31.01.2028 → 29.02.2028.

### 2.4. Статусы и просрочка

```
is_overdue   = paid_at IS NULL ? today > due_date     // не оплачено и срок прошёл
                               : paid_at > due_date    // оплачено с опозданием
overdue_days = (paid_at ?? today) - due_date, если > 0, иначе 0
```

Отображение в UI (4 визуальных состояния):

| Состояние | Условие | Цвет |
|---|---|---|
| Ожидает оплаты | не оплачено, `today ≤ due` | нейтральный, «через N дн.» / «сегодня» |
| Просрочено | не оплачено, `today > due` | красный, «просрочка N дн.» |
| Оплачено | оплачено, `paid_at ≤ due` | зелёный |
| Оплачено с опозданием | оплачено, `paid_at > due` | жёлтый, «опоздание N дн.» |

Правила изменения:

- Отметить оплату: `paid_at` обязателен (по умолчанию сегодня), не позже сегодняшнего дня.
- Отменить оплату: `paid_at = NULL` (дата очищается).
- Исправить фактическую дату: меняется только `paid_at`; `due_date` не меняется никогда → просрочка пересчитывается.
- Отметка — только для конкретного периода. Просрочка одного периода не мешает следующим.

### 2.5. Генерация периодов

- При создании платежа периоды создаются **в той же транзакции**, поэтому они сразу видны в списке.
- Затем планировщик раз в минуту дозаполняет периоды. Правило горизонта: создать все периоды с
  `due_date ≤ today + OCCURRENCES_LOOKAHEAD_DAYS` (по умолчанию 31) **и** как минимум один период в будущем.
  Для ежемесячного платежа это обычно «текущий + следующий». Это и нужно на демо (шаг 7 — «следующий период с отдельным статусом»).
- Если первая дата в прошлом, прошлые периоды тоже создаются (и сразу видна просрочка). Ограничение на старте:
  `first_due_date ≥ today − 365 дней`, чтобы не нагенерировать сотни строк.
- Идемпотентность: `UNIQUE (recurring_payment_id, period_index)` + `INSERT … ON CONFLICT DO NOTHING`.

### 2.6. Прекращение платежа (DELETE)

`DELETE /recurring-payments/{id}` — это **прекращение с сохранением истории**, а не удаление строки:

1. `ended_at = now()`, `ended_by = admin`.
2. Удаляются только будущие неоплаченные периоды (`due_date > today AND paid_at IS NULL`).
3. Прошлые периоды (оплаченные и неоплаченные) остаются, в UI с пометкой «платёж прекращён».
4. Планировщик фильтрует `ended_at IS NULL` → новых периодов и напоминаний нет («удалённый платёж не напоминает»).

### 2.7. Валюты и суммы

- Только `RUB`, `USD`, `EUR` (CHECK в БД + валидация). Конвертации нет.
- В БД — `amount_minor BIGINT` (копейки/центы), в API — строка `"120000.00"`: без float-ошибок.
- Итоги **всегда по каждой валюте отдельно**, никогда не складываем разные валюты.
- У периода хранится снимок суммы и валюты: если когда-нибудь появится изменение суммы шаблона, история не перепишется.

### 2.8. Напоминания

- Окно: неоплаченный период и `0 ≤ due_date − today ≤ REMINDER_DAYS_BEFORE` (по умолчанию 3, валидация `≥ 3`, т.к. кейс требует «минимум за 3 дня»).
- Время: плановые напоминания — не раньше `REMINDER_HOUR` (09:00 местного), чтобы не писать ночью.
  **Исключение:** если платёж (период) появился уже внутри окна, отправляем сразу
  («добавили платёж позже, чем за 3 дня до срока → напоминание сразу»). Планировщик ещё и «пинается» после создания платежа, поэтому не ждём минуту.
- Без дублей: таблица `reminder_deliveries` с `UNIQUE (occurrence_id, channel, kind)`.
  Алгоритм — outbox: вставить строку `pending` (`ON CONFLICT DO NOTHING RETURNING`) → отправить → `sent`.
  При ошибке — `failed` + `next_attempt_at` с экспоненциальной задержкой, повтор тем же процессом.
- Оплаченный период в выборку не попадает. Если оплату отменили внутри окна и напоминания ещё не было — оно уйдёт на следующем тике; если было — повторно не шлём.
- Несколько инстансов бэкенда: `pg_try_advisory_lock` на задачу планировщика, напоминания не задвоятся.
- Сообщение: название, сумма, валюта, дата срока (обязательный минимум кейса) + период и кнопки.

## 3. База данных (миграции)

Существующие: `000001_users`, `000002_refresh-token`. Новые:

### 000003_recurring_payments (P0)

```sql
CREATE TABLE recurring_payments (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title           TEXT        NOT NULL CHECK (char_length(title) BETWEEN 1 AND 100),
    amount_minor    BIGINT      NOT NULL CHECK (amount_minor > 0),
    currency        CHAR(3)     NOT NULL CHECK (currency IN ('RUB', 'USD', 'EUR')),
    interval_months SMALLINT    NOT NULL DEFAULT 1 CHECK (interval_months IN (1, 3, 6, 12)),
    first_due_date  DATE        NOT NULL,
    anchor_day      SMALLINT    NOT NULL CHECK (anchor_day BETWEEN 1 AND 31),
    category        TEXT,                               -- P1
    note            TEXT,
    created_by      UUID REFERENCES users(id) ON DELETE SET NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    ended_at        TIMESTAMPTZ,                        -- прекращён (soft delete)
    ended_by        UUID REFERENCES users(id) ON DELETE SET NULL
);
CREATE INDEX idx_recurring_payments_active ON recurring_payments (id) WHERE ended_at IS NULL;
```

### 000004_payment_occurrences (P0)

```sql
CREATE TABLE payment_occurrences (
    id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    recurring_payment_id UUID    NOT NULL REFERENCES recurring_payments(id) ON DELETE RESTRICT,
    period_index         INTEGER NOT NULL CHECK (period_index >= 0),
    due_date             DATE    NOT NULL,
    amount_minor         BIGINT  NOT NULL CHECK (amount_minor > 0),
    currency             CHAR(3) NOT NULL CHECK (currency IN ('RUB', 'USD', 'EUR')),
    paid_at              DATE,                              -- фактическая дата оплаты
    paid_marked_by       UUID REFERENCES users(id) ON DELETE SET NULL,
    paid_marked_at       TIMESTAMPTZ,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (recurring_payment_id, period_index)
);
CREATE INDEX idx_occurrences_due_date ON payment_occurrences (due_date);
CREATE INDEX idx_occurrences_unpaid   ON payment_occurrences (due_date) WHERE paid_at IS NULL;
```

`ON DELETE SET NULL` у ссылок на пользователя: удаление пользователя не ломает историю оплат.

### 000005_reminder_deliveries (P0)

```sql
CREATE TABLE reminder_deliveries (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    occurrence_id   UUID NOT NULL REFERENCES payment_occurrences(id) ON DELETE CASCADE,
    channel         TEXT NOT NULL CHECK (channel IN ('telegram', 'email', 'webhook')),
    kind            TEXT NOT NULL CHECK (kind IN ('due_soon', 'due_today', 'overdue')),
    status          TEXT NOT NULL CHECK (status IN ('pending', 'sent', 'failed')),
    attempts        INTEGER NOT NULL DEFAULT 0,
    last_error      TEXT,
    next_attempt_at TIMESTAMPTZ,
    external_ref    TEXT,           -- telegram: "<chat_id>:<message_id>" для правки сообщения
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    sent_at         TIMESTAMPTZ,
    UNIQUE (occurrence_id, channel, kind)
);
```

### 000006_telegram (P1/P2)

```sql
ALTER TABLE users ADD COLUMN telegram_user_id  BIGINT UNIQUE;
ALTER TABLE users ADD COLUMN telegram_username TEXT;

CREATE TABLE telegram_link_codes (

```

### 000007_audit_log (P1 «Логи»)

```sql
CREATE TABLE audit_log (
    id          BIGSERIAL PRIMARY KEY,
    at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    actor_id    UUID,            -- без FK: лог переживает удаление пользователя
    actor_login TEXT,
    action      TEXT NOT NULL,   -- auth.login_ok, auth.login_failed, payment.create, occurrence.mark_paid, ...
    entity_type TEXT,
    entity_id   TEXT,
    ip          INET,
    details     JSONB            -- например {"paid_at": {"old": "2026-10-20", "new": "2026-10-19"}}

CREATE INDEX idx_audit_log_at ON audit_log (at DESC);
```

### 4.3. API — полный контракт

Все пути с префиксом `/api/v1`. Ошибки новых эндпоинтов — JSON через уже существующий `api.WriteError`:

```json
{ "error": { "code": "validation_failed", "message": "amount must be positive",
             "request_id": "…", "details": { "field": "amount" } } }
```

Каталог кодов: `unauthorized`, `forbidden`, `validation_failed`, `not_found`, `login_taken`,
`admin_immutable`, `occurrence_not_paid`, `paid_at_in_future`, `rate_limited`, `feature_disabled`.
Хендлеры пользователей сейчас отвечают plain text; их стоит перевести на тот же JSON, чтобы фронту было с чем работать единообразно.

#### Регулярные платежи

| Метод | Путь | Роль | Описание |
|---|---|---|---|
| GET | `/recurring-payments?include_ended=false&q=` | user, admin | список шаблонов (пользователь видит только чтение) |
| POST | `/recurring-payments` | admin | создать; сразу генерирует периоды и «пинает» напоминания |
| DELETE | `/recurring-payments/{id}` | admin | прекратить с сохранением истории (2.6) |
| GET | `/recurring-payments/preview?first_due_date=&interval_months=` | admin | P1: ближайшие 3 даты — подсказка в форме |

`POST` тело:

```json
{ "title": "Аренда офиса", "amount": "120000.00", "currency": "RUB",
  "first_due_date": "2026-10-26", "interval_months": 1,
  "category": "Офис", "note": "договор №17" }
```

Ответ `201`: шаблон + `next_due_date` + `occurrences_created` + `reminder_scheduled_now: true|false`
(чтобы фронт показал «Срок ближе 3 дней — напоминание отправлено сразу»).

Валидация: `title` 1–100; `amount` > 0, не больше 2 знаков после запятой, ≤ 10^12;
`currency ∈ {RUB, USD, EUR}`; `first_due_date ≥ today − 365`; `interval_months ∈ {1,3,6,12}`.

#### Периоды (платежи)

| Метод | Путь | Роль | Описание |
|---|---|---|---|
| GET | `/payment-occurrences` | user, admin | список с фильтрами, сортировкой, пагинацией |
| GET | `/payment-occurrences/{id}` | user, admin | один период + все периоды этого платежа (история) |
| PATCH | `/payment-occurrences/{id}` | user, admin | оплатить / отменить / исправить дату |

Фильтры `GET`: `status=paid|unpaid`, `overdue=true|false`, `currency=RUB` (можно несколько),
`due_from`, `due_to`, `recurring_payment_id`, `q` (по названию), `include_ended=true`,
`sort=due_date|amount|title`, `order=asc|desc`, `limit` (≤ 200), `offset`.

Элемент ответа:

```json
{ "id": "…", "recurring_payment_id": "…", "title": "Аренда офиса",
  "amount": "120000.00", "currency": "RUB", "due_date": "2026-10-26",
  "period_label": "2026-10", "status": "unpaid", "paid_at": null,
  "is_overdue": false, "overdue_days": 0, "days_until_due": 3,
  "recurring_ended": false, "paid_marked_by": null }
```

`PATCH` — три формы тела:

```json
{ "status": "paid", "paid_at": "2026-10-25" }   // paid_at опционален, по умолчанию сегодня
{ "status": "unpaid" }                           // paid_at очищается
{ "paid_at": "2026-10-24" }                      // исправить дату; только если уже оплачено, иначе 409 occurrence_not_paid
```

`paid_at` в будущем → `422 paid_at_in_future`. Ответ — обновлённый период (с пересчитанной просрочкой).
Каждое изменение пишется в `audit_log` со старым и новым значением.

#### Итоги

`GET /payments/summary?from=2026-10-01&to=2026-10-31` (по умолчанию — текущий месяц, по `due_date`):

{ "from": "2026-10-01", "to": "2026-10-31",

P1 «Итоги на дату»: `?as_of=2026-11-15` — всё со сроком ≤ даты: оплачено vs осталось.

### 4.5. Планировщик

- Одна горутина, `time.Ticker(SCHEDULER_INTERVAL)`, первый прогон сразу при старте (после рестарта ничего не теряется — всё в БД).
- Задачи по порядку: `GenerateOccurrences` → `SendReminders` → (P1) `SendOverdueReminders`, `DailyDigest`.
- Каждая задача под `pg_try_advisory_lock(<id задачи>)`; не взяли блокировку — пропускаем тик.
- `Kick()` — неблокирующий сигнал в канал: вызывается после создания платежа и после отмены оплаты, чтобы реагировать за секунды.
- Остановка по `ctx` вместе с graceful shutdown HTTP-сервера.

### 4.6. Telegram-бот

- Транспорт — long polling (`getUpdates`): работает локально без публичного URL. Один потребитель на токен.
- Пустой `TELEGRAM_BOT_TOKEN` → бот выключен с предупреждением в логе; всё остальное работает.
- Формат напоминания (`parse_mode=HTML`, с экранированием):

```
🔔 Напоминание об оплате
Аренда офиса
Сумма: 120 000,00 ₽ (RUB)
Срок: 26.10.2026 — через 3 дня
Период: октябрь 2026
[✅ Оплачено]  [📱 Открыть]
```

- Кнопка «✅ Оплачено» (P1 из списка жюри): `callback_data = "paid:<occurrence_id>"` (41 байт < 64).
  Обработчик: находит пользователя по `from.id` → если не привязан, `answerCallbackQuery` с подсказкой
  «Привяжите Telegram в профиле»; иначе ставит `paid_at = сегодня`, редактирует сообщение
  («✅ Оплачено 23.10.2026 — Иван Петров») и убирает кнопку. Пишет аудит.
- Кнопка «📱 Открыть» — ссылка `https://t.me/<bot>/<app>?startapp=occ_<id>` (inline-кнопки `web_app` в группах запрещены, а ссылка на Mini App работает).
- Если оплату отметили в вебе после напоминания — (P1) правим сообщение в чате по `external_ref`.
- Команды: `/start link_<code>` (привязка), `/chatid` (показывает id чата — помогает настроить `.env`),
  `/today`, `/week`, `/overdue`, `/summary` (P1), свободный текст в личке → ассистент (P2).
- На 429 от Telegram — ждём `retry_after`; на сетевые ошибки — повтор через outbox.

### 4.7. Тестовые данные (P0: «тестовые данные команда готовит сама»)

`SEED_DEMO=true` (и `make seed`), идемпотентно по логинам и названиям. Даты считаются от «сегодня», поэтому демо всегда выглядит живым:

## 5. Веб-панель (Nuxt 4)

> Папку `frontend/` я не трогаю — это план для того, кто делает фронт.

### 5.1. Техническая основа

- **SPA** (`ssr: false`): панель за авторизацией, SEO не нужен, а SSR усложняет пересылку кук. Mini App — в том же билде на `/tg/*`.
- UI-кит: Nuxt UI (таблицы, модалки, формы, тосты, тёмная тема из коробки) — экономит время на хакатоне.
- Composables:
  - `useApi()` — обёртка над `$fetch`: базовый `/api/v1`, `credentials: 'include'`, при 401 — один общий
    (single-flight) `POST /auth/refresh` и повтор запроса; если refresh не удался — на `/login`.
  - `useAuth()` — текущий пользователь (`GET /auth/me`), `isAdmin`, `login()`, `logout()`.
  - `useMoney()` — `Intl.NumberFormat('ru-RU', { style: 'currency', currency })`; суммы приходят строками.
  - `useDates()` — формат `dd.MM.yyyy`, «сегодня», «через N дн.», «просрочка N дн.».
- Route middleware: без сессии → `/login`; не-админ на админской странице → `/`. Это только UX — защита на бэкенде.
- Dev: прокси `/api` → `localhost:8080` (Nitro `devProxy`), чтобы был один origin и работали куки `SameSite=Strict`.

### 5.2. Навигация

Сайдбар: **Обзор**, **Платежи**, **Календарь** (P1), **Регулярные**, **Пользователи** (admin), **Журнал** (admin, P1), **Настройки** (admin).
Шапка: строка «Спросить…» (⌘K, P2), имя пользователя, бейдж роли, выход. На мобильном — нижний таб-бар.

### 5.3. Страницы

**`/login`**
- Логин, пароль, «Войти». 401 → «Неверный логин или пароль»; 429 → «Слишком много попыток, подождите минуту».
- Без авторизации никакие страницы и данные не доступны (критерий приёмки).

**`/` — Обзор**
- Три карточки-валюты (RUB / USD / EUR), в каждой за текущий месяц: «К оплате», «Оплачено», «Просрочено»
  (`GET /payments/summary`). Валюты никогда не суммируются между собой.
- Красный блок «Просрочено» — список с кнопкой «Отметить оплату» прямо в строке.
- «Ближайшие 7 дней» — что и когда оплатить.
- P1: график-прогноз на 6 месяцев по валютам.

**`/payments` — список платежей (главный экран кейса)**
- Фильтры: переключатель месяца «‹ Октябрь 2026 ›» (или диапазон), статус (Все / Не оплачено / Оплачено / Просрочено),
  чипы валют, поиск по названию, тумблер «Показывать прекращённые».
- Таблица — ровно то, что требует кейс:

| Название | Период | Срок | Сумма | Валюта | Статус | Дата оплаты | Просрочка | |
|---|---|---|---|---|---|---|---|---|
| Аренда офиса · ежемесячно | окт 2026 | 26.10.2026 | 120 000,00 ₽ | RUB | Ожидает · через 3 дн. | — | — | ✓ |
| Аренда офиса · ежемесячно | сен 2026 | 18.09.2026 | 120 000,00 ₽ | RUB | Оплачено | 20.09.2026 | опоздание 2 дн. | ⋯ |

- Действия в строке:
  - «Отметить оплату» → поповер с датой (по умолчанию сегодня, максимум сегодня) → `PATCH`;
  - «Изменить дату оплаты» → тот же поповер → `PATCH {paid_at}`, просрочка пересчитывается на глазах;
  - «Отменить оплату» → подтверждение → `PATCH {status: "unpaid"}`.
  - Оптимистичное обновление с откатом при ошибке, тост с результатом.
- Футер таблицы: итоги по каждой валюте для текущего фильтра.
- Клик по строке → боковая панель: все периоды этого платежа (история), журнал изменений, P1 чек/ссылка.

**`/recurring` — Регулярные платежи**
- Таблица шаблонов: Название, Сумма, Валюта, Периодичность, День оплаты, Следующий срок, Статус (активен / прекращён).
- Пользователь видит только чтение. Админ:
  - «Добавить платёж» (модалка): Название; Сумма (ввод с разделителями тысяч, > 0, ≤ 2 знаков);
    Валюта (сегменты RUB / USD / EUR); Дата ближайшей оплаты (подсказка: «31-го → в коротких месяцах последний день»);
    Периодичность (по умолчанию «Ежемесячно»); Категория, Комментарий.
    Под формой превью «Следующие сроки: 31.01, 28.02, 31.03».
    После сохранения тост: «Напоминание придёт 23.10» или «Срок ближе 3 дней — напоминание отправлено сразу».
  - «Прекратить» → модалка: «Новые периоды и напоминания перестанут создаваться. История оплат сохранится.»

**`/users` — Пользователи (admin)**
- Таблица: Имя, Логин, Роль, Создан, Telegram (привязан / нет).
- Строка админа — бейдж «из .env», без кнопок действий.
- Создать (ФИО, логин, пароль + «сгенерировать»), изменить (ФИО, логин), удалить (с подтверждением). 409 → «Логин уже занят».

**`/settings` (admin)**
- Telegram: статус бота (@username, подключён ли), чат для напоминаний, кнопка «Отправить тестовое сообщение».
- Напоминания: за сколько дней (≥ 3), с какого часа. Часовой пояс — только показ (задаётся в `.env`).
- P1: SMTP, webhook.

**`/profile`** — ФИО, логин, «Привязать Telegram» (deep link с кодом) / «Отвязать».

**`/calendar` (P1)** — сетка месяца, в днях — суммы с цветом статуса; клик по дню → список.

**`/audit` (P1, admin)** — журнал с фильтрами по пользователю, действию, дате.

### 5.4. UX-детали, которые жюри заметит

- Скелетоны при загрузке, понятные пустые состояния («Платежей пока нет — добавьте первый» для админа,

## 6. Telegram Mini App (P2)

### 6.1. Как открывается

- В @BotFather: `/newapp` (или кнопка меню бота) → URL `https://<DOMAIN>/tg`. Нужен HTTPS:
  на проде есть nginx + `scripts/cert.sh`, локально — туннель (cloudflared / ngrok).
- Точки входа: кнопка меню бота, кнопка «📱 Открыть» в напоминании (`startapp=occ_<id>` → сразу карточка периода).

### 6.2. Авторизация

1. Mini App берёт `Telegram.WebApp.initData` и шлёт `POST /api/v1/auth/telegram`.
2. Бэкенд проверяет подпись: `secret = HMAC_SHA256(key="WebAppData", msg=bot_token)`,
   `hash == hex(HMAC_SHA256(secret, data_check_string))`, `auth_date` не старше 24 часов.
3. Ищет пользователя по `telegram_user_id`:
   - найден → выдаёт access/refresh **в теле ответа** (в WebView надёжнее Bearer, чем куки);
   - не найден → экран «Войдите один раз логином и паролем» → `POST /auth/telegram/link` привязывает и логинит.
4. Роли и ограничения — те же, проверяются тем же бэкендом.

### 6.3. Экраны

- **Главная:** баннер «Просрочено: 2», «Ближайшие 7 дней», три карточки валют за месяц.
- **Список:** чипы-фильтры (Все / Не оплачено / Просрочено / Оплачено, валюты), группы «Просрочено / На этой неделе / Позже».
- **Карточка периода:** сумма крупно, срок, статус; `MainButton` «Оплачено сегодня»; «Выбрать другую дату»; «Отменить оплату»;
  `HapticFeedback.notificationOccurred('success')` после отметки.
- **Спросить (P2):** поле ввода и примеры вопросов → ассистент (раздел 7).
- **Админ:** «+ Добавить платёж» — та же форма, что в вебе, адаптированная под телефон.
- Цвета из `Telegram.WebApp.themeParams` → CSS-переменные (светлая/тёмная тема Telegram), `BackButton` для навигации,
  `WebApp.ready()` и `expand()` при старте.

## 7. Запросы на естественном языке (P2)

### 7.1. Что умеет

Строка «Спросить…» в вебе (⌘K), экран в Mini App и свободный текст боту в личке.

| Запрос | Что происходит |
|---|---|
| «Что просрочено?» | список просроченных периодов |
| «Сколько мы платим в долларах в месяц?» | итоги по USD (+ месячный эквивалент для квартальных/годовых) |
| «Что надо оплатить до конца недели?» | периоды с `due_to = воскресенье` |
| «Покажи подписки дороже 50 евро» | поиск по названию/категории + фильтр по сумме |
| «Сколько потратили на аренду за полгода?» | итоги по оплаченным за диапазон |
| «Отметь аренду за октябрь оплаченной вчера» | **предложение действия** → кнопка «Подтвердить» |
| «Добавь интернет 1500 рублей каждое 5 число» (admin) | **предложение создать платёж** → «Подтвердить» |

### 7.2. Устройство

- `POST /api/v1/assistant/query` `{ "question": "…", "history": [последние 6 реплик] }` →
  `{ "answer": "текст", "blocks": [{ "type": "occurrences", "items": [...] }, { "type": "summary", ... }], "pending_action": { "id", "kind", "description" } | null }`.
- `POST /api/v1/assistant/actions/{id}/confirm` — выполняет подтверждённое действие через обычный сервис.
- **LLM никогда не пишет SQL и ничего не меняет сам.** Ей даются инструменты (tools) — тонкие обёртки над теми же сервисами,
  вызываемые от имени текущего пользователя, поэтому права (раздел 4.4) соблюдаются автоматически:
  - чтение: `search_occurrences {status, overdue, currency, due_from, due_to, paid_from, paid_to, title_query, min_amount, max_amount, limit≤50}`,
    `get_summary {from, to, currency?}`, `list_recurring_payments {include_ended, title_query}`;
  - запись (только предложение, без исполнения): `propose_mark_paid {occurrence_id, paid_at}`, `propose_mark_unpaid {occurrence_id}`,
    `propose_create_recurring_payment {…}` — последний **передаётся модели только для админа**, и сервис ещё раз проверит роль при подтверждении.
  - Предложения хранятся в `assistant_actions` (`user_id`, `kind`, `payload`, `expires_at` = 10 мин, `status`).
- Цикл: Go SDK `github.com/anthropics/anthropic-sdk-go`, ручной цикл tool use (≤ 5 итераций), инструменты со
  `strict: true` (гарантированно валидный JSON аргументов), `tool_choice: auto` — принудительный выбор инструмента
  на `claude-opus-5-5` не поддерживается (400).
- Модель: по умолчанию `claude-opus-5-5` с `effort: low` (быстро и дёшево для такого объёма). Модель задаётся
  `ASSISTANT_MODEL` — при желании можно поставить `claude-haiku-5-5`, это решение команды по бюджету.
- Кэширование промпта: системный промпт и список инструментов — стабильный префикс с `cache_control`; изменчивое
  (сегодняшняя дата, часовой пояс, роль, имя) — в сообщение пользователя, иначе кэш будет промахиваться.
- Отказы модели: проверять `stop_reason` перед чтением ответа, включить серверные fallbacks (`fallbacks: "default"`, beta `server-side-fallback-2026-07-01`).
- Защита: rate limit 20 запросов/мин на пользователя, таймаут 30 с, вопрос и вызванные инструменты — в аудит,
  в модель уходят только данные о платежах (без паролей, токенов, логинов других людей).
- Ответ рисуем не только текстом: блоки `occurrences` / `summary` рендерятся теми же компонентами, что и таблица и карточки.
  Из них можно сразу нажать «Отметить оплату».

### 7.3. Риск

Claude API недоступен из ряда регионов, включая Россию: запросы к API должны уходить с сервера в поддерживаемом регионе.
Если демо-сервер в РФ — фича работать не будет. Поэтому она за флагом (`ANTHROPIC_API_KEY`), и без неё остальное приложение работает полностью.

### 8.2. Наши идеи

- **Ежедневный дайджест** в чат в 09:00: что сегодня, что просрочено, что на неделе (одно сообщение вместо пачки).
- **Повторные напоминания**: в день срока и на следующий день после него (виды `due_today`, `overdue`, каждый один раз).
- **Команды бота** `/today`, `/week`, `/overdue`, `/summary`, `/chatid`.
- **Месячный эквивалент**: «в месяц по USD» с учётом квартальных и годовых платежей (годовой / 12).
- **Экспорт CSV/XLSX** списка с фильтрами; **импорт CSV** платежей для админа.
- **Индексация суммы** с определённого периода (аренда подорожала с января) — меняет только будущие периоды.
- **Пауза платежа** без прекращения.
- **Демо-режим** `DEMO_TODAY`: на защите «перематываем время», чтобы показать следующий период и просрочку, не дожидаясь месяца.
- **PWA**: установка панели на телефон.

## 10. Тестирование

- **Юнит (`domain/schedule`)**, табличные тесты:
  - 31.01 → 28.02 → 31.03 → 30.04; 31.01.2028 → 29.02.2028; 30-е и 29-е числа; квартал и год;
  - просрочка: оплата в день срока — вовремя; на следующий день — просрочка 1 дн.; исправление даты убирает просрочку;
  - окно напоминаний: за 4 дня — нет, за 3 / 2 / 0 — да, после срока — нет (`due_soon`).
- **Сервисы** с фейковыми репозиториями: генерация идемпотентна; прекращение удаляет только будущие неоплаченные;
  выбор напоминаний не берёт оплаченные, прекращённые и уже отправленные; созданный внутри окна платёж — сразу.
- **HTTP (httptest)**: матрица прав — каждый админский эндпоинт пользователем → 403, без токена → 401.
- **Интеграционные** на реальном Postgres (docker): миграции up/down, уникальные ограничения, `ON CONFLICT`.
- **E2E-скрипт** `scripts/demo.sh` (curl): проходит шаги 1–7 и проверяет коды ответов — заодно репетиция защиты.
- Перезапуск: поднять, отметить оплату, `docker compose restart backend` → данные на месте, повторного напоминания нет.

## 11. Чек-лист приёмки (из кейса → где закрыто)

| Критерий | Чем закрываем |
|---|---|
| Запуск по README | `docker compose -f docker-compose.local.yaml up` поднимает БД, миграции, бэкенд, **фронт и nginx** (сейчас в локальном compose фронта нет — добавить), README пошагово |

| OpenAPI-файл + рабочий Swagger | `backend/docs/swagger.yaml`, `GET /api/v1/docs` |
| Эндпоинты из кейса | все пути раздела 4.3 совпадают с таблицами кейса |

Логин → список платежей → обзор → регулярные → пользователи → настройки.

Кнопка «Оплачено» в Telegram и правка сообщения → аудит → календарь → итоги на дату → webhook/email → бюджет → чеки.

### Этап D — P2

Привязка Telegram → Mini App → ассистент.

## 13. Открытые вопросы и риски

- **Telegram-чат и токен для жюри.** Если жюри запускает у себя, им нужен свой бот. В README пошагово:
  @BotFather → токен → добавить бота в группу → `/chatid` → вписать в `.env`. Без токена приложение работает, просто без напоминаний.
- **Доступ к api.telegram.org** с хостинга — предусмотрен `TELEGRAM_API_URL` для прокси.
- **Claude API** — региональные ограничения (7.3), фича за флагом.
- **Смена `ADMIN_LOGIN` в `.env`** создаст второго администратора, а старый останется (и через API его не удалить).
  Варианты: при старте понижать или удалять админов с другим логином. Решить до защиты.
- **Mini App требует HTTPS** — для показа нужен прод-домен или туннель.
- **Secure-куки на http://localhost** — Chrome и Firefox принимают, Safari нет → флаг `COOKIE_SECURE`.
